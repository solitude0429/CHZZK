# CHZZK hardening notes

This document summarizes the extension hardening invariants for the MV2 required-permission CHZZK HLS redirect architecture.

## Runtime behavior

- A minimal MV2 `site-observer.js` content script runs at `document_start` on CHZZK live pages (`https://*.chzzk.naver.com/live` and `https://*.chzzk.naver.com/live/*`) and prewarms only the CHZZK live tab identity before the first playlist request; the first redirect must not depend solely on content-script timing.
- The persistent background entrypoint is orchestration-only at the main subsystem boundaries: `playlist-probe.js` owns bounded network/HLS evidence resolution, while `session-state-store.js` owns expiry, LRU ordering, resolution cancellation, and redirected-request cleanup. Each module accepts explicit policy or collaborator inputs, so network, timer, cleanup, and eviction behavior can be tested independently. Both remain bundled into the single MV2 background script, so the split changes maintainability rather than permissions or runtime loading.
- Install/startup and content-message prewarming never blindly clear in-memory state: each delayed tab result is re-read through `tabs.get()` under the same per-tab transition token before reusable verified contextless targets, matching response records, or an eligible origin-bound dedicated master observer may migrate into the confirmed live context. A newer mini-player/navigation transition, unresolved generic work, or unverified numeric work makes the snapshot ineligible.
- Trusted HLS master responses are filtered only to copy at most `probeMaxBytes` for local parsing while every byte is immediately written through unchanged. An exact successful response URL/status is scored before the filter closes, so the best valid target by resolution, frame rate, then bitrate is available for the first numeric rendition request without a duplicate fetch. Observer records are released on filter stop/error, terminal completion/error, ineligible redirect, a pending redirect from a dedicated host to a generic CDN at a context boundary, generic-CDN or destructive context migration, and tab closure. An eligible dedicated-livecloud observer survives a same-tab, same-stream mini-player transition only while its current or pending redirect URL remains dedicated, just as an eligible master-to-master redirect chain retains it. A bounded fetch fallback is used only when response filtering or redirect lifecycle observation cannot attach. Per-context tokens reject every master response that outlives an eligible context.
- Only case-complete `.m3u8` URL patterns enter the blocking `webRequest` listener; media segments bypass it entirely. Trusted numeric HLS playlist requests share one 50 ms request-level `blockingProbeBudgetMs` deadline across tab-trust validation and candidate resolution, while an already-cached target returns a synchronous redirect without a Promise or timer turn. Target state, resolved state, and in-flight work are independently keyed by tab, live context, and a secret-free playlist family; query, fragment, quality markers, and recognized signed path-tail segments are excluded from that family key, and the key is never persisted in diagnostics. Expired state is swept and the combined target/failure/resolution set is LRU-bounded per tab and globally.
- A same-document live-to-mini-player or mini-player-to-mini-player transition re-keys only trusted master-derived or verified dedicated-livecloud targets, eligible dedicated master observers whose current or pending redirect URL remains dedicated, and the one unambiguous still-running dedicated candidate scan or response verification per playlist family under the new transition token. Matching rendition verifiers are re-keyed rather than guessed to belong to the retired player: verification sequence makes a newer mini-player request supersede an older failure, and a genuine failure from a first mini-player request that started before `tabs.onUpdated` still invalidates the target. This prevents a 50 ms fail-open request from causing an immediate duplicate scan and playback stall without discarding response authority. Generic-CDN work, observers awaiting a generic redirect, conflicting source contexts, aborted work, full document loads, foreign navigation, new live contexts, and closed tabs still abort and cannot restore state later.
- Candidate probe redirects fail closed because Firefox does not expose redirect hops to manual Fetch handling. Requested and final URLs must match exactly at the network layer after removing only a client-side fragment, which Fetch neither transmits nor retains in `Response.url`; path and query changes remain rejected. A response must have an exact first meaningful `#EXTM3U` line plus a structurally usable master variant, media segment, or LL-HLS part reference; an `#EXT-X-GAP` media segment and an `#EXT-X-PART` marked `GAP=YES` are explicitly unavailable and do not count as usable evidence. The response must not declare an obvious HTML/JSON content type and is capped in UTF-8 bytes. A returned master must contain a trusted variant whose metadata and URI both prove that candidate.
- Ordinary media-playlist bodies do not declare their rendition resolution, so numeric evidence relies on the same safe URL-marker grammar used by rewriting, including the accepted `/360p/.../chunklist_480p.m3u8` legacy form. This assumption is bounded to one playlist family and a 30-second `markerEvidenceTtlMs` idle timeout, equal to the code maximum. A newly observed trusted master replaces an earlier numeric-fallback target in either direction. The resulting master-derived target remains authoritative for its live context: an in-flight or scheduled numeric probe cannot promote it to a rendition the master did not advertise, while a later trusted master can legitimately promote it; a lower later master cannot demote still-valid master evidence. For both redirected and already-selected-quality requests, Firefox's response filter immediately writes every chunk through to the player while incrementally decoding at most `probeMaxBytes`, avoiding a second joined byte-array copy. A chunk-write or filter error is sticky and cannot be overwritten by later body completion. Network-event identity strips only the client-side URL fragment before exact comparison because Firefox does not send fragments. Only a successful 2xx completion whose exact streamed body is usable HLS evidence renews the timeout; HTTP status alone does not. The sole bodyless exception is an exact-network-URL HTTP 304 whose exact URL previously passed body validation, because Firefox reuses that cached playlist; body emptiness waits for completion status so event order cannot turn revalidation into a failure. Per-target epochs and monotonic verification order prevent an older overlapping failure from invalidating newer exact-target success. A genuine older failure is deferred while a newer exact-target verifier is pending, discarded only after newer success, and applied if that newer verifier is merely client-cancelled. Firefox `NS_BINDING_ABORTED` and `NS_ERROR_ABORT` remain exact neutral client-cancellation codes because overlapping LL-HLS requests are routinely superseded; the cancellation itself neither renews nor invalidates target state. Bodyless HTTP 204/205, other 3xx, 4xx/5xx, an unavailable response filter, an empty/HTML/malformed, gap-only, or oversized non-304 body, a final-URL mismatch, or another `onErrorOccurred` result invalidates and temporarily suppresses that target. The lower numeric fallback schedules its first upward retry at the failed higher target's backoff expiry, while subsequent unresolved refreshes return to the normal interval.
- The first request records its live-channel context before probing. Explicit non-CHZZK document/origin metadata vetoes and evicts cached trust. A same-site non-live CHZZK document can continue small-player playback only for playlists on the two dedicated livecloud host suffixes; it cannot authorize a generic trusted CDN. A URL-only live-to-list/search SPA route change migrates only a trusted master-derived or verified dedicated-host target, one whose numeric response verifier successfully attached and remains pending/valid, an eligible dedicated master observer, or one unambiguous dedicated candidate scan into an authoritative mini-player context. Firefox may continue reporting the original live `documentUrl` after that `pushState`; while mini-player mode is authoritative, stale live metadata cannot re-adopt the retired live context or restart probes. Unresolved generic work, unattached/failed numeric verification, generic-CDN targets and master observers, collisions, expired evidence, and failed-target suppression are discarded; full document loads also remove the prior target. These transitions still remove concrete live-page trust, while live-page changes, foreign navigation, tab close, and request-proven context mismatch abort the corresponding fetches and invalidate state so stale async work cannot resurrect cross-context trust. When Firefox supplies only the CHZZK origin and omits the page path, a generic CDN additionally requires an authoritatively prewarmed live tab; otherwise only the dedicated-host exception remains. Adopting a concrete live context invalidates older contextless work unless a startup query authoritatively binds reusable verified contextless state or an eligible origin-bound dedicated master observer to that same live tab.
- Same-URL loading clears only quality/session evidence. When Firefox omits the update URL, the background validates `tabs.get(tabId).url`; an existing mini-player marker remains authoritative during that asynchronous window so stale live request metadata cannot enable a generic CDN. A still-live tab regains live trust after validation, while navigation or tab close cannot be re-trusted by the stale asynchronous result.
- Contextless compatibility is limited to numeric playlists on the dedicated `livecloud.pstatic.net.live.gscdn.net` and `nvelop-livecloud.pstatic.net` host suffixes when all page metadata is absent. Generic CDN path markers are never contextless trust evidence, and any contradictory metadata vetoes the exception.
- Quality rewriting uses one shared pathname grammar for parsing and replacement; only real `.m3u8` pathnames are eligible and query/hash bytes are never rewritten. Contradictory markers fail closed except for the observed `/360p/.../chunklist_480p.m3u8` legacy shape, whose two markers are rewritten together.
- Redirect handling and startup prewarming are independent of local diagnostics persistence; storage failures cannot extend the blocking request deadline or prevent already-open live tabs from being trusted after install/startup.
- Local diagnostics storage writes are serialized and exact-schema normalized on load/save. Arrays are tail-bounded by policy, corrupt counters reset to zero, valid counters saturate at `Number.MAX_SAFE_INTEGER`, unknown fields are dropped, and the popup normalizes again before rendering. Runtime transitions use fixed action/reason/source enums and retain only normalized qualities and timestamps; raw error strings, tab IDs, signed URLs, subdomains, and ports are excluded.

## Content script behavior

- `site-observer.js` is scoped to `https://chzzk.naver.com/live` and `https://chzzk.naver.com/live/*` and only sends `chzzk.live-page-ready`.
- The content script does not query or mutate the CHZZK page DOM.
- Firefox may omit or retain stale message sender URL fields, so the background treats them as non-authoritative and queries the current tab URL under a per-tab transition token before accepting prewarm. A delayed `tabs.get()` result from a document that entered mini-player mode or navigated away cannot restore live-tab trust, while a still-current live result migrates only reusable verified contextless state.

## Permissions and data

- Firefox manifest version 2 is used so the CHZZK origin and trusted CDN origins are declared in required `permissions`, like the user's other Firefox extensions. The full CHZZK origin permission is needed for Firefox to expose dedicated livecloud requests initiated by same-origin list/search pages to `webRequest`; the content script remains live-page-only and runtime policy rejects non-live generic-CDN requests.
- No `host_permissions`, `optional_permissions`, or `optional_host_permissions` site-access toggle surface is used for core functionality; the MV2 content script match is required install-time CHZZK live access.
- No external telemetry/data collector is used by the extension runtime.
- `data_collection_permissions` declares `required: ["none"]`.
- Diagnostic URL labels retain only a canonical allowlist domain and media shape; full subdomains and ports are discarded before local persistence/export.

## Verification

`npm run verify` includes:

- `npm run format:check`
- generated runtime refresh
- manifest/project validation
- semantic workflow validation
- ESLint and web-ext lint
- Node unit/security/transaction tests
- shared-module line/function/branch thresholds (95%/95%/80%) and non-vacuous VM-bundle named-function/executable-byte thresholds (80%/65%)
- dependency audit
- deterministic package build/audit

CI also runs the checksum-pinned Firefox Developer Edition functional-only E2E. It proves a synthetic `480p` playlist is redirected to the available `1080p` fixture without altering the signed-style query and proves the synthetic `AddonManager.findUpdates` path in an isolated profile. It does not establish Release authenticity.

## Release invariants

- `package.json`, `manifest.json`, and immutable release metadata must describe the same extension version.
- Version bumps use canonical `a.b.c` only: no leading zero, no prerelease/build suffix, and at most 9 digits per component. MAJOR is for incompatible changes, MINOR for backward-compatible features, and PATCH for backward-compatible bug/security fixes.
- `policy/quality-policy.json` is the source of truth for fallback candidates, probe budgets, and trusted domains.
- AMO receives only the deterministic exact-allowlist ZIP, including `LICENSE` and `NOTICE`; local untracked files and symlinks cannot enter the signing input.
- Release metadata has one exact validator shared by prepare/sign/structure/update/deploy callers: fixed project identity/repository/update URL, exact keys and runtime paths, unique paths, canonical names, safe sizes, and SHA-256/Git digest syntax.
- Authorized AMO API requests reject redirects. Only an exact approved developer-file URL 404 is retried; every attempt starts there with a fresh JWT, while manually validated redirect hops receive no authorization. API JSON and signed bodies have streaming byte/depth bounds.
- The Node signed-XPI check is structural-only. It applies compressed, per-entry, aggregate, ratio, exact signature-name/size, comment-free ZIP, ZIP64/multi-disk, raw-path, and full local-entry-contiguity limits before JSZip inflation. It does not implement Mozilla cryptography.
- Release authenticity requires the separate stock-Firefox gate with default signature enforcement, permanent installation, exact ID/version/update URL, and `SIGNEDSTATE_SIGNED`. The release workflow runs install mode on the final AMO-signed XPI before attestation/draft staging; after production deployment, the checked-in native Windows wrapper runs update mode against the actual client Firefox in separate disposable profiles, drives both the per-extension manual discovery/install controls and the default global `about:addons` update control, and persists only a non-overwriting, at-most-4-KiB fixed-schema success result containing Firefox version, extension version, installed state, and final `none-found` state. Its documented process-scoped execution-policy bypass changes no persistent Windows policy, and the wrapper clears then restores Node startup/trust-injection variables around both Node invocations.
- Build, AMO-secret signing, signed verification, OIDC attestation, and `contents: write` draft staging are separate Actions jobs. Actions never receives the administrator token and never publishes the draft.
- One out-of-band `release` operation binds the configured operator, protected clean exact head, canonical version, fresh 128-bit nonce, and enabled immutable-release setting; dispatches and boundedly waits for the exact actor/source/branch/workflow run; then repeats the head/checkout checks before loading the protected finalizer. Before AMO, compatible partial drafts are recognized only after exact commit/tag/name/byte verification. After attested staging, the finalizer verifies three stable draft snapshots and all build attestations, rechecks the protected default head, operator, clean local branch/head, and version, checks the admin-only immutable setting, then performs one final protected-head read immediately before patching only the exact release ID to `draft=false` and requires the exact immutable post-state. Existing exact immutable state is a verified no-op; mismatch, timeout, failed/duplicate run, or orphan tag states fail closed.
- Internal deployment is exposed only through an owner-only external `.mjs` bootstrap. An already-running trusted parent shell disables tracing, removes dynamic-loader, shell-startup, Node, proxy, and CA injection variables, then passes the token only over stdin through a clean-parent marker; the bootstrap starts absolute system Node under a second `/usr/bin/env -i`. Trusted Git must report the supplied checkout itself as the canonical top-level with the pinned repository origin. Against that complete root, the bootstrap rejects an invoked realpath inside the checkout or outside a private operator-owned parent and requires an operator-owned file with exact mode `0500`. It uses root-owned absolute Git/GitHub CLI, a private tool home, a pinned repository name and numeric ID, a protected remote default-head and exact clean local-head binding, Git-blob verification of the complete deployment source graph, and a hash-pinned JSZip bundle before sealed execution; the checkout entrypoint refuses direct loading. Parent ownership of the private execution tree also removes the artifact-download directory after terminal child failure. The client then requires the Release's independent immutable flag, derives `updates.json` from verifier-returned Release metadata and signed-XPI buffers, and never rereads a validated path for activation. The landing page uses root-absolute immutable release paths and its tests require every linked local artifact to exist, so serving `index.html` through the stable root symlink cannot turn same-directory links into 404s. Deployment normalizes the target path, rejects symlinked, externally owned, or group/world-writable managed paths, and serializes mutation with a process-bound advisory lock whose child and cleanup waits are bounded. Before release or live-link mutation it fsyncs a private durable snapshot journal; a killed process or reboot therefore releases the lock and the next run restores the previous generation before retrying. Link and release post-verification remain inside the rollback boundary so an unverified generation never stays live.
- Atomic artifact writes fsync file data and their parent directory, source files are copied from a single verified open descriptor, and source ZIP/metadata/signed XPI/update links use exact canonical basenames.
- Repository settings can run only through an owner-only external `.mjs` bootstrap after the same no-trace trusted-parent boundary. It pins the canonical repository name and numeric ID, exact admin identity, protected remote head, clean local default-branch head, and protected configurator Git blob before sealed execution with absolute tools and a private tool home. Secret inspection is name/scope-only and blocks all writes while manual environment-secret migration remains. Apply is sequential rather than atomic; a bounded value-free recovery report and a fresh dry-run support safe convergence after partial API failure. Any payload-preparation read completes before a final protected-head read immediately preceding every mutation.
- Repository protection requires a native pull request with zero required approvals, the four GitHub-Actions-bound checks `analyze`, `dependency-review`, `firefox-e2e`, and `verify`, administrator enforcement, strict up-to-date heads, and zero unresolved conversations. Semantic workflow validation restricts triggers to the six project-approved GitHub events so an unsupported webhook name cannot reach the server as a zero-job workflow. The final direct Codex review is the single qualitative review layer: its review record must name the current full PR head after the body and high-risk notes are final, every later source push requires a new review, and the owner verifies that identity immediately before the manual squash merge. The retired custom review-completion workflow cannot provide the claimed merge-time guarantee because GitHub checks are commit-scoped, reusable across PRs with the same commit, and asynchronously invalidated after PR or request metadata changes. Native pull-request and conversation-resolution controls independently block direct pushes and unresolved review threads. A duplicate bot-review status, commit-scoped qualitative status, positive approval count, and impossible sole-owner self-approval are intentionally absent. Actions are limited to GitHub-owned actions, workflow tokens default to read-only, only squash merges are enabled, and merged branches are deleted automatically. AMO credentials exist only as protected `firefox-signing` environment secrets; same-name repository copies are rejected. Version-update bot PRs and Scorecard SARIF are omitted because they created recurring queue/alert noise; exact dependency pins, `npm audit`, dependency review, CodeQL, custom fuzzing, secret scanning, and immutable releases retain the actionable security coverage.
