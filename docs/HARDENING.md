# CHZZK hardening notes

This document summarizes the extension hardening invariants for the MV2 required-permission CHZZK playback architecture.

## Runtime behavior

- The blocking `webRequest` registration combines case-complete HLS playlist patterns with an exact CHZZK ad-state API allowlist. The ad branch requires trusted CHZZK page metadata, a valid tab, a GET XHR, and the exact API host before it cancels a known schedule/poll route or strips only the `dt` live/video-detail token; unrelated API traffic fails open.
- A minimal MV2 `site-observer.js` content script runs at `document_start` on CHZZK live pages (`https://*.chzzk.naver.com/live` and `https://*.chzzk.naver.com/live/*`) and prewarms only the CHZZK live tab identity before the first playlist request; the first redirect must not depend solely on content-script timing.
- The persistent background entrypoint is orchestration-only at the main subsystem boundaries: `playlist-probe.js` owns bounded network/HLS evidence resolution, while `session-state-store.js` owns expiry, LRU ordering, resolution cancellation, and redirected-request cleanup. Each module accepts explicit policy or collaborator inputs, so network, timer, cleanup, and eviction behavior can be tested independently. Both remain bundled into the single MV2 background script, so the split changes maintainability rather than permissions or runtime loading.
- Install/startup and content-message prewarming never blindly clear in-memory state: each delayed tab result is re-read through `tabs.get()` under the same per-tab transition token before reusable verified contextless targets, matching response records, or an eligible origin-bound dedicated master observer may migrate into the confirmed live context. A newer mini-player/navigation transition, unresolved generic work, or unverified numeric work makes the snapshot ineligible.
- Trusted HLS master responses are filtered only to copy at most `probeMaxBytes` for local parsing while every byte is immediately written through unchanged. An exact successful response URL/status is scored before the filter closes, so the best valid target by resolution, frame rate, then bitrate is available for the first numeric rendition request without a duplicate fetch. Observer records are released on filter stop/error, terminal completion/error, ineligible redirect, a pending redirect from a dedicated host to a generic CDN at a context boundary, generic-CDN or destructive context migration, and tab closure. An eligible dedicated-livecloud observer survives a same-tab, same-stream mini-player transition only while its current or pending redirect URL remains dedicated, just as an eligible master-to-master redirect chain retains it. A bounded fetch fallback is used only when response filtering or redirect lifecycle observation cannot attach. A valid observed response cancels older fallback master fetches under every bounded source family retained for its trusted redirect chain before applying rendition-family authority, so differing source, hop, and rendition family keys cannot let stale fallback evidence rotate current lineage. Per-context tokens reject every master response that outlives an eligible context.
- Only case-complete `.m3u8` URL patterns enter the HLS branch of the blocking listener; media segments bypass it entirely. Trusted numeric HLS playlist requests share one 50 ms request-level `blockingProbeBudgetMs` deadline across tab-trust validation and candidate resolution, while an already-cached target returns a synchronous redirect without a Promise or timer turn. Target state, resolved state, and in-flight work are independently keyed by tab, live context, and a secret-free playlist family; query, fragment, quality markers, and recognized signed path-tail segments are excluded from that family key, and the key is never persisted in diagnostics. Expired state is swept and the combined target/failure/lineage/resolution set is LRU-bounded per tab and globally.
- A same-document live-to-mini-player or mini-player-to-mini-player transition re-keys only trusted master-derived or verified dedicated-livecloud targets, their matching secret-free failure suppression and master lineage, eligible dedicated master observers whose current or pending redirect URL remains dedicated, and the one unambiguous still-running dedicated candidate scan or response verification per playlist family under the new transition token. Matching rendition verifiers are re-keyed rather than guessed to belong to the retired player: verification sequence makes a newer mini-player request supersede an older failure, and a genuine failure from a first mini-player request that started before `tabs.onUpdated` still invalidates the target. This prevents a 50 ms fail-open request from causing an immediate duplicate scan and playback stall without discarding response authority. Generic-CDN work, observers awaiting a generic redirect, conflicting source contexts, aborted work, full document loads, foreign navigation, new live contexts, and closed tabs still abort and cannot restore state later.
- Candidate probe redirects fail closed because Firefox does not expose redirect hops to manual Fetch handling. Requested and final URLs must match exactly at the network layer after removing only a client-side fragment, which Fetch neither transmits nor retains in `Response.url`; path and query changes remain rejected. A response must have an exact first meaningful `#EXTM3U` line plus a structurally usable master variant, media segment, or LL-HLS part reference; an `#EXT-X-GAP` media segment and an `#EXT-X-PART` marked `GAP=YES` are explicitly unavailable and do not count as usable evidence. The response must not declare an obvious HTML/JSON content type and is capped in UTF-8 bytes. A returned master must contain a trusted variant whose metadata and URI both prove that candidate.
- Ordinary media-playlist bodies do not declare their rendition resolution, so numeric evidence relies on the same safe URL-marker grammar used by rewriting, including the accepted `/360p/.../chunklist_480p.m3u8` legacy form. This assumption is bounded to one playlist family and a 30-second `markerEvidenceTtlMs` idle timeout, equal to the code maximum. A newly observed trusted master replaces an earlier numeric-fallback target in either direction. The resulting master-derived target remains authoritative for its live context: an ordinary in-flight or scheduled numeric probe cannot promote it to a rendition the master did not advertise, while a later trusted master can legitimately promote it; a lower later master cannot demote still-valid master evidence. The numeric promotion exception is confined to matching-lineage recovery after a genuine same-family failure: it checks the exact advertised quality first and, if that remains unavailable, may prove a configured intermediate quality above the current fallback without crossing the advertised ceiling. Secret-free lineage retains only the advertised/recovery quality, bounded timing, and an in-memory epoch; every recovery URL is rebuilt transiently from the current media request so the current signed query is used and no signed URL enters lineage or failure state. A newer master rotates the lineage epoch before normal target precedence is evaluated, even when all of its variants are temporarily suppressed, so an aborted or late recovery completion cannot restore a rendition the newer master omitted. For both redirected and already-selected-quality requests, Firefox's response filter immediately writes every chunk through to the player while incrementally decoding at most `probeMaxBytes`, avoiding a second joined byte-array copy. A chunk-write or filter error is sticky and cannot be overwritten by later body completion. Network-event identity strips only the client-side URL fragment before exact comparison because Firefox does not send fragments. Only a successful 2xx completion whose exact streamed body is usable HLS evidence renews the timeout; HTTP status alone does not. The sole bodyless exception is an exact-network-URL HTTP 304 whose exact URL previously passed body validation, because Firefox reuses its cached playlist; body emptiness waits for completion status so event order cannot turn revalidation into a failure. Per-target epochs and monotonic verification order prevent an older overlapping failure from invalidating newer exact-target success. A genuine older failure is deferred while a newer exact-target verifier is pending, discarded only after newer success, and applied if that newer verifier is merely client-cancelled. Firefox `NS_BINDING_ABORTED` and `NS_ERROR_ABORT` remain exact neutral client-cancellation codes because overlapping LL-HLS requests are routinely superseded; the cancellation itself neither renews nor invalidates target state. Bodyless HTTP 204/205, other 3xx, 4xx/5xx, an unavailable response filter, an empty/HTML/malformed, gap-only, or oversized non-304 body, a final-URL mismatch, or another `onErrorOccurred` result invalidates and temporarily suppresses that target. Known-failure recovery starts at the failed higher target's backoff expiry and then retries at most every 15 seconds on playlist traffic; unrelated numeric discovery keeps its normal one-minute interval.
- The first request records its live-channel context before probing. Explicit non-CHZZK document/origin metadata vetoes and evicts cached trust. A same-site non-live CHZZK document can continue small-player playback only for playlists on the legacy dedicated suffixes or exact `livecloud.akamaized.net` URLs with an exact `chzzk` path segment; it cannot authorize a generic trusted CDN. A URL-only live-to-list/search SPA route change migrates only a trusted master-derived or verified dedicated-host target, its matching secret-free failure suppression and master lineage, one whose numeric response verifier successfully attached and remains pending/valid, an eligible dedicated master observer, or one unambiguous dedicated candidate scan into an authoritative mini-player context. Firefox may continue reporting the original live `documentUrl` after that `pushState`; while mini-player mode is authoritative, stale live metadata cannot re-adopt the retired live context or restart probes. Unresolved generic work, unattached/failed numeric verification, generic-CDN targets and master observers, collisions, and expired evidence are discarded; full document loads also remove the prior target, failure suppression, and lineage. These transitions still remove concrete live-page trust, while live-page changes, foreign navigation, tab close, and request-proven context mismatch abort the corresponding fetches and invalidate state so stale async work cannot resurrect cross-context trust. When Firefox supplies only the CHZZK origin and omits the page path, a generic CDN additionally requires an authoritatively prewarmed live tab; otherwise only the dedicated-host exception remains. Adopting a concrete live context invalidates older contextless work unless a startup query authoritatively binds reusable verified contextless state or an eligible origin-bound dedicated master observer to that same live tab.
- Same-URL loading clears only quality/session evidence. When Firefox omits the update URL, the background validates `tabs.get(tabId).url`; an existing mini-player marker remains authoritative during that asynchronous window so stale live request metadata cannot enable a generic CDN. A still-live tab regains live trust after validation, while navigation or tab close cannot be re-trusted by the stale asynchronous result.
- Contextless compatibility is limited to numeric playlists on the legacy dedicated `livecloud.pstatic.net.live.gscdn.net` and `nvelop-livecloud.pstatic.net` host suffixes, plus the exact current `livecloud.akamaized.net` host only when its path contains an exact `chzzk` segment, when all page metadata is absent. Generic CDN path markers are never contextless trust evidence, and any contradictory metadata vetoes the exception.
- Quality rewriting uses one shared pathname grammar for parsing and replacement; only real `.m3u8` pathnames are eligible and query/hash bytes are never rewritten. Contradictory markers fail closed except for the observed `/360p/.../chunklist_480p.m3u8` legacy shape, whose two markers are rewritten together.
- Redirect handling and startup prewarming are independent of local diagnostics persistence; storage failures cannot extend the blocking request deadline or prevent already-open live tabs from being trusted after install/startup.
- Local diagnostics storage writes are serialized and exact-schema normalized on load/save. Arrays are tail-bounded by policy, corrupt counters reset to zero, valid counters saturate at `Number.MAX_SAFE_INTEGER`, unknown fields are dropped, and the popup normalizes again before rendering. Runtime transitions use fixed action/reason/source enums and retain only normalized qualities and timestamps; raw error strings, tab IDs, signed URLs, subdomains, and ports are excluded.

## Content script behavior

- The MAIN-world bundle neutralizes only decrypted typed-array JSON with a nonempty request ID and the current protocol version. GFP schedules require a recognized live, event-live, or VOD schedule ID, and every break must use an ad unit from the matching live-or-VOD family plus nonempty record-only sources. VOD recognizes only `w_chzzk_naver_va` and `w_chzzk_naver_va_mid`; the unobserved `w_chzzk_naver_va_post` fails open. NAVER waterfalls require a recognized live/VOD unit, record event tracking, a finite random number, and populated ads. The guard preserves response context, empties only recognized ad collections, and fails open for malformed, crossed, mixed, unobserved, or unrelated payloads.
- Narrow styles suppress only CHZZK's known ad-blocking layer, dimmed/ad UI, and the exact `#live_rs_banner` and `#vod_rs_banner` elements with zero layout; unrelated banners remain rendered.
- `site-observer.js` is scoped to `https://chzzk.naver.com/live` and `https://chzzk.naver.com/live/*` and only sends `chzzk.live-page-ready`.
- `player-controller.js` is a separate Firefox MAIN-world content script loaded across the already-required CHZZK origin. It enforces quality wherever the document contains the player, including live, home, following, search, category, and mini-player routes. It binds only the current `videoTracks` add/remove/change events and removes those listeners on replacement or stop.
- Discovery prioritizes the current `#live_player_layout` React fiber and the public PZP wrapper's `videoTracks`, then uses scoped-video, bounded descendant, legacy custom-element, and global-video fallbacks. One scan may inspect at most 1,024 unique fiber nodes and 1,024 unique React state values. A preview video cannot outrank the live layout.
- Every scan chooses the highest concrete manual track by resolution, pixel count, and `videoBitrate`. The quality pane and its filter are observation/UI signals, never target authority. A stored or confirmed descriptor is a high-water mark, and setter-triggered remounts are re-resolved before persistence so detached generations cannot commit storage.
- Configurable `selected` accessors are guarded synchronously. ABR/lower `true` assignments are discarded when the highest track is current, or redirected to the highest accessor before the lower page setter runs. The guard detects same-object descriptor replacement, rebinds remounts, and restores the exact prior own or inherited descriptor on stop. The pane filter wrapper likewise preserves and restores the exact original descriptor and never overwrites a page replacement.
- Player-root mutations scan without the former 250 ms cold-start delay. Other mutation bursts are coalesced; track, route, resize, orientation, viewport, waiting, stalled, playing, and canplay evidence schedule bounded checks. A one-second watchdog catches silent late tracks and demotions. There is no `timeupdate` listener, and unchanged highest-quality state performs no selection write.
- Asynchronous controller-owned selections use read-only confirmation. A controller-wide budget begins with four writes, is not reset by route, pane, filter, player, or track-list churn, and refills at most one write per five seconds. Ignored writes cool down instead of causing unbounded playlist reloads.
- Each MAIN-world controller uses a non-enumerable page-global singleton, stops a prior current-generation instance, and starts one current instance. On an open tab updated from an older quality-controller generation, unremovable old listeners may still fire, but the new synchronous track guard prevents their lower-track setter from reaching the player. The bundle has no extension API or media URL access, never invents a track, and writes only real CHZZK tracks plus the official storage value.
- Firefox may omit or retain stale message sender URL fields, so the background treats them as non-authoritative and queries the current tab URL under a per-tab transition token before accepting prewarm. A delayed `tabs.get()` result from a document that entered mini-player mode or navigated away cannot restore live-tab trust, while a still-current live result migrates only reusable verified contextless state.

## Permissions and data

- Firefox manifest version 2 is used so the CHZZK origin and trusted CDN origins are declared in required `permissions`, like the user's other Firefox extensions. The existing CHZZK origin permission covers exact ad-state API handling and exposes dedicated livecloud requests initiated by same-origin list/search pages to `webRequest`; the isolated prewarmer remains live-page-only, the page-only MAIN runtime has no extension API, and runtime policy rejects foreign metadata and non-live generic-CDN requests.
- No `host_permissions`, `optional_permissions`, or `optional_host_permissions` site-access toggle surface is used for core functionality; the MV2 content script match is required install-time CHZZK live access.
- No external telemetry/data collector is used by the extension runtime.
- `data_collection_permissions` declares `required: ["none"]`.
- Diagnostic URL labels retain only a canonical allowlist domain and media shape; full subdomains and ports are discarded before local persistence/export.

## Verification

`npm run verify` includes:

- `npm run format:check`
- generated runtime refresh
- manifest/project validation
- semantic workflow validation
- ESLint and web-ext lint
- Node unit/security/transaction tests
- shared-module line/function/branch thresholds (95%/95%/80%) and non-vacuous VM-bundle named-function/executable-byte thresholds (80%/65%)
- dependency audit
- deterministic package build/audit

CI also runs the checksum-pinned Firefox Developer Edition functional-only E2E. It uses current `livecloud.akamaized.net/chzzk` and `stream_hls_*` request shapes; proves both master-derived selection and a masterless concurrent numeric probe batch reach `1080p` without altering the signed-style query; and verifies home/live/following SPA enforcement, delayed `addtrack`, and a filter-vetoed cold compact load. Its responsive fixture models the current DIV layout, React wrapper bridge, class-based pane, and configurable prototype track accessor. Across physical 1200 → 560 → 1200 resizing, four page-owned compact lower-track setter attempts must produce no lower setter commit, no added `waiting`, `stalled`, or `emptied` event, and no wide-return recovery write. A separate remount fixture replaces every player/track/pane identity at each breakpoint. The update fixture starts with a 0.1.21-shaped legacy MAIN-world controller, updates the still-open document through `AddonManager.findUpdates`, proves its old lifecycle handlers remain alive, and requires the new guard to neutralize their lower-track attempts without a reload. This E2E establishes functional behavior, not Release authenticity or proprietary decoder equivalence.

## Release invariants

- `package.json`, `manifest.json`, and immutable release metadata must describe the same extension version.
- Version bumps use the UTC calendar as canonical `YY.M.D`: no leading zero in month/day, no prerelease/build suffix, and at most one immutable Release per UTC day.
- `policy/quality-policy.json` is the source of truth for fallback candidates, probe budgets, and trusted domains.
- AMO receives only the deterministic exact-allowlist ZIP, including `LICENSE` and `NOTICE`; local untracked files and symlinks cannot enter the signing input.
- Release metadata has one exact validator shared by prepare/sign/structure/update/deploy callers: fixed project identity/repository/update URL, exact keys and runtime paths, unique paths, canonical names, safe sizes, and SHA-256/Git digest syntax.
- Authorized AMO API requests reject redirects. Only an exact approved developer-file URL 404 is retried; every attempt starts there with a fresh JWT, while manually validated redirect hops receive no authorization. API JSON and signed bodies have streaming byte/depth bounds.
- The Node signed-XPI check is structural-only. It applies compressed, per-entry, aggregate, ratio, exact signature-name/size, comment-free ZIP, ZIP64/multi-disk, raw-path, and full local-entry-contiguity limits before JSZip inflation. It does not implement Mozilla cryptography.
- Release authenticity requires the separate stock-Firefox gate with default signature enforcement, permanent installation, exact ID/version/update URL, and `SIGNEDSTATE_SIGNED`. The release workflow runs install mode on the final AMO-signed XPI before attestation/draft staging; after production deployment, the checked-in native Windows wrapper runs update mode against the actual client Firefox in separate disposable profiles, drives both the per-extension manual discovery/install controls and the default global `about:addons` update control, and persists only a non-overwriting, at-most-4-KiB fixed-schema success result containing Firefox version, extension version, installed state, and final `none-found` state. Its documented process-scoped execution-policy bypass changes no persistent Windows policy, and the wrapper clears then restores Node startup/trust-injection variables around both Node invocations.
- Build, AMO-secret signing, signed verification, and OIDC attestation are separate Actions jobs. Actions has read-only repository contents, never receives the administrator credential, and cannot create or publish a GitHub Release.
- The Windows `chzzk` operator binds the local `gh` keyring identity, numeric repository ID, protected clean exact head, UTC version, fresh nonce, and immutable-release setting. It records a COMMENT review against the final exact PR head, merges with `--match-head-commit`, reuses an exact successful signed artifact when available, verifies all three attestations locally, and checks the complete draft asset set before publishing the exact Release ID. Existing exact immutable state is a verified no-op; mismatched source, tag, assets, duplicate run, or changed setting fails closed.
- Internal deployment uses local `gh` only. The PC downloads and attestation-verifies the immutable Release, bundles the protected activator and import graph into one ESM file, and sends that file plus the three canonical assets through `ssh server` in a private `/srv/admin` directory. The server receives no checkout, GitHub CLI, token, or `node_modules`. The activator fixes the target path, validates deploy/rollback direction while holding the process lock, keeps an fsynced recovery journal until backend and Caddy verification succeeds, and restores the previous links on failure.
- After activation, the PC independently verifies the production HTTPS manifest, provenance, MIME types, links, and digest, then uses Scoop Firefox ESR and geckodriver with a disposable profile to prove the previous signed XPI updates to the new signed version. The user's Firefox profile is never opened or modified.
- Atomic artifact writes fsync file data and their parent directory, source files are copied from a single verified open descriptor, and source ZIP/metadata/signed XPI/update links use exact canonical basenames.
- Repository settings are read and changed directly by the authenticated local `gh` operator after exact repository, administrator identity, and protected-head readback. No bot, token-forwarding bootstrap, or comment-triggered workflow is part of the operating path.
- Repository protection requires a native pull request with zero required approvals, the four GitHub-Actions-bound checks `analyze`, `dependency-review`, `firefox-e2e`, and `verify`, administrator enforcement, strict up-to-date heads, and zero unresolved conversations. Semantic workflow validation restricts triggers to the six project-approved GitHub events so an unsupported webhook name cannot reach the server as a zero-job workflow. The final direct Codex review is the single qualitative review layer: its review record must name the current full PR head after the body and high-risk notes are final and the PR is Ready, every later source push requires a new review, and the acting owner or explicitly authorized operating agent verifies that identity immediately before the squash merge. An owner instruction to finish or merge the scoped task supplies that authorization without a second confirmation after all gates pass; GitHub auto-merge and unattended generic merge automation remain forbidden. The retired custom review-completion workflow cannot provide the claimed merge-time guarantee because GitHub checks are commit-scoped, reusable across PRs with the same commit, and asynchronously invalidated after PR or request metadata changes. Native pull-request and conversation-resolution controls independently block direct pushes and unresolved review threads. A duplicate bot-review status, commit-scoped qualitative status, positive approval count, and impossible sole-owner self-approval are intentionally absent. Actions are limited to GitHub-owned actions, workflow tokens default to read-only, only squash merges are enabled, GitHub auto-merge is disabled, and merged branches are deleted automatically. AMO credentials remain a complete pair at Repository Actions or protected `firefox-signing` environment scope; a partial pair at either scope is rejected, and the sign job remains bound to the protected environment. Version-update bot PRs and Scorecard SARIF are omitted because they created recurring queue/alert noise; exact dependency pins, `npm audit`, dependency review, CodeQL, custom fuzzing, secret scanning, and immutable releases retain the actionable security coverage.
