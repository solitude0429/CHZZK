# Security Policy

## Threat model

This extension handles narrowly identified CHZZK ad-state responses and live-page HLS playlist requests to remove video ads, redirect eligible playlist quality URLs, and keep local troubleshooting diagnostics. The main risks are:

- capturing unrelated CDN or non-CHZZK traffic;
- storing signed media URL query strings;
- broad redirects affecting non-CHZZK pages;
- accidentally publishing account/session identifiers in exported diagnostics, fixtures, issues, or PRs.

## Controls

- Ad-request handling accepts only exact CHZZK API routes with trusted CHZZK page metadata. The MAIN-world guard also requires the current protocol version and exact paired CHZZK schedule/ad-unit identities for live or VOD; every VOD break must use a currently observed base or mid unit and contain only populated record sources. It preserves response envelopes, empties only ad collections, and fails open for malformed, crossed, unobserved, mixed, or unrelated data.
- No `scripting` permission. Page mutations are limited to neutralizing recognized CHZZK ad payloads/UI and selecting a real CHZZK player track with its official local-storage preference.
- `site-observer.js` stays isolated and scoped to CHZZK live pages; it sends only a live-page-ready prewarm message and never accesses page objects. The separate `player-controller.js` runs in Firefox's MAIN world because the player rejects synthetic menu clicks. It loads across the already-required CHZZK origin so home-to-live SPA entry is covered, then applies the exact `/live` or `/lives` pathname guard on every selection scan. It has no extension API, request URL, credential, or diagnostics access; binds only the current player's track-list events; and selects only a concrete track accepted by CHZZK's own quality filter. Because Firefox may omit or stale message sender URL fields and asynchronous tab snapshots, the background queries the current tab under a per-tab transition token and accepts prewarm only while its current URL is still a CHZZK live page and no newer navigation or mini-player transition occurred; only reusable verified contextless state may migrate.
- No external telemetry/data collector is used by the extension runtime.
- The Firefox manifest declares no data collection/transmission with `data_collection_permissions.required: ["none"]`.
- Firefox MV2 required permissions include the CHZZK origin (`https://*.chzzk.naver.com/*`) and trusted HLS CDN origins needed by `webRequest`, HLS availability probes, and redirects. Runtime policy still limits same-site non-live playback to the legacy dedicated suffixes plus exact-host, exact-path current Akamai traffic; the MAIN-world player controller uses that existing origin access but its per-scan mutation scope is limited to exact `/live` and `/lives` paths.
- No `host_permissions` or optional host permission surface is used for core functionality; the MV2 content script match is required install-time CHZZK live access.
- Local diagnostics storage mutations are serialized and exact-schema normalized on load/save to avoid local read-modify-write races and corrupted/unbounded persisted state. Invalid counters reset to zero, valid counters saturate at the safe-integer maximum, arrays are tail-trimmed to policy, and unknown fields are dropped.
- No global static or session DNR ruleset.
- Request handling is constrained by tab, CHZZK context, trusted request domains, request methods, and resource types. The HLS branch requires an actual case-complete `.m3u8` pathname, while the ad branch uses an exact CHZZK API route allowlist and strips only the `dt` detector token from exact live/video-detail requests; media segments and unrelated API routes bypass both branches. Explicit non-CHZZK document/origin metadata always vetoes cached trust. A same-site non-live CHZZK page can continue small-player playback only on the legacy dedicated suffixes or exact `livecloud.akamaized.net` URLs with an exact `chzzk` path segment, and cannot authorize a generic CDN playlist. A URL-only live-to-list/search SPA route change migrates only a trusted master-derived or verified dedicated-host target with its matching secret-free failure suppression and master lineage, one whose numeric response verifier actually attached and has not failed, an eligible dedicated master observer whose current or pending redirect URL remains dedicated, or one unambiguous dedicated candidate scan into authoritative mini-player state. Matching response verifiers remain ordered under the new context instead of being classified by an unobservable player owner: a newer request supersedes an older failure, while the first mini-player request remains able to invalidate unusable evidence even when Firefox delivers it before `tabs.onUpdated`. Stale original-live `documentUrl` metadata cannot re-adopt the old context, including during URL-less reload validation. Unresolved generic work, unattached/failed numeric verification, generic-CDN targets and master observers, dedicated observers awaiting a generic redirect, collisions, expired evidence, full document loads, concrete live-page trust, and all foreign-navigation state are removed.
- Contextless compatibility is limited to numeric playlists on `livecloud.pstatic.net.live.gscdn.net` and `nvelop-livecloud.pstatic.net` (including their subdomains), plus exact `livecloud.akamaized.net` URLs with an exact `chzzk` path segment, when page metadata is entirely absent. Other Akamai hosts and paths remain generic CDN traffic. Generic CDN path markers are never contextless trust evidence, and contradictory metadata always vetoes this exception.
- The first request records its live context. Target state, secret-free master lineage, failed-target suppression, resolved evidence, and in-flight work are keyed by tab, live context, and secret-free playlist family. Independent families cannot share results, expired entries are swept where applicable, and the combined state is LRU-bounded per tab and globally. Only eligible dedicated-livecloud target, matching failure/lineage, master-observer, response-verification, and unambiguous candidate-scan state may be re-keyed under a new token across a same-document mini-player transition; generic-CDN work, conflicting contexts, full document loads, new live contexts, foreign navigation, tab close, and request-proven mismatch invalidate the corresponding work and trust.
- URL-marker-only media evidence is restricted to its playlist family and a 30-second `markerEvidenceTtlMs` idle timeout. Redirected and already-selected-quality response chunks are passed to the player immediately and copied only up to `probeMaxBytes`; renewal requires both a successful 2xx completion and an exact streamed body that passes HLS/quality validation. An empty HTTP 304 may renew only when that exact network URL previously passed body validation, independent of body/status event order. Target epochs and request ordering make newer valid evidence authoritative over stale overlapping failures. A genuine older failure is deferred only while a newer verifier is pending; newer success discards it, while a neutral Firefox `NS_BINDING_ABORTED`/`NS_ERROR_ABORT` cancellation applies it so the failure cannot disappear. The cancellation itself cannot renew or invalidate the target; status alone, an unavailable verifier, empty/HTML/malformed/gap-only or oversized non-304 bodies, other redirects, other browser-visible errors, and HTTP 204/205 or 4xx/5xx completions invalidate and temporarily suppress it. The first retry occurs at the failed higher target's bounded backoff expiry; known-failure recovery then runs at most every 15 seconds while ordinary discovery remains at one minute. Master recovery stores only secret-free quality/timing/epoch lineage, first rebuilds the exact advertised quality from the current same-family media request, and retains no signed recovery URL. After an exact miss, the same guarded cycle may prove only configured qualities above the current fallback and no higher than the advertised ceiling. Every valid newer master rotates the epoch even when all of its variants are temporarily suppressed, and a valid observed response cancels older fallback master fetches from every bounded source retained across its redirect chain before applying rendition-family authority. A recovery completion must match the current context, target epoch, lineage epoch, family, and quality before it can restore the target.
- Diagnostics persistence is fire-and-forget relative to blocking requests and prewarming, so storage or error-reporting failures cannot extend the request deadline or prevent live tabs from being prewarmed. Install/startup and content-message handlers migrate reusable verified contextless state or an eligible origin-bound dedicated master observer only after re-reading the current live tab under an unchanged transition token, preventing delayed delivery from erasing a target or master response that playback established first, forcing another probe, or overwriting newer mini-player state.
- Numeric URL rewriting and response renewal use the same bounded pathname-marker grammar. Signed query strings and fragments are preserved byte-for-byte. Contradictory pathname markers fail closed except for the explicitly observed `/360p/.../chunklist_480p.m3u8` legacy form, whose markers are rewritten together and whose valid response body renews the selected target without periodic re-probing.
- Probe bodies require `#EXTM3U` as the exact first meaningful line plus a usable master variant, media segment, or LL-HLS part reference; an `#EXT-X-GAP` media segment and an `#EXT-X-PART` with `GAP=YES` are unavailable and cannot establish or renew quality evidence. Probe bodies reject obvious HTML/JSON MIME types and are capped in UTF-8 bytes. HLS attributes reject duplicate keys and accept only bounded positive decimal bandwidth/frame-rate syntax.
- HLS diagnostics use an allowlist model: canonical domain label, normalized quality, structured media shape, and fixed runtime-transition enums only. Userinfo, complete paths, query strings, fragments, signed path values, high-entropy tokens, raw browser errors, tab identifiers, full subdomains and ports are discarded before persistence/export. The popup renders only the shared normalized schema.
- The release workflow separates read-only build, AMO-secret signing, signed-artifact verification, and OIDC provenance into different jobs. It accepts exact protected-head `workflow_dispatch` inputs (`source_sha`, UTC `YY.M.D` `version`, and a nonce), permanently installs the final AMO-signed XPI in checksum-pinned stock Firefox with default signature enforcement, and emits only the three canonical files plus provenance as a run artifact. It cannot create, edit, or publish a GitHub Release. The `firefox-signing` environment remains limited to protected branches.
- Signing uses a dependency-free Node AMO client and an exact deterministic prepared ZIP. Secret-bearing jobs do not checkout, install packages, or hold repository/OIDC write authority; derived AMO JWTs are scoped to API-root requests plus the exact first unlisted developer-file download, authorized requests use manual/error redirect handling, and later signed-XPI redirect hops never carry authorization.
- The public operator is `npm run chzzk -- status|ship|release|deploy|rollback` on the Windows PC. It uses only the local GitHub CLI keyring, pins the repository ID and protected remote head before mutations, and never exports or persists the raw credential. Read-only requests run only `status` and readbacks. Product-changing requests authorize `ship`; tooling and documentation changes stop after protected merge.
- The local `release` operation dispatches one exact nonce-bound signed-asset run, waits for its exact workflow/source/run identity, downloads and verifies the canonical artifact and provenance, then creates or resumes only a compatible draft and publishes that exact Release ID after fresh immutable-setting and protected-head readback. Actions never receives administrator authority or creates the draft. Foreign tag/source/assets, duplicate runs, or different bytes fail closed.
- Internal update deployment downloads and attestation-verifies Release assets locally, bundles the exact protected activator, its complete import graph, and `jszip` into one self-contained ESM file with esbuild, then sends that file and the three canonical assets as a private uniquely named bounded SCP bundle over the internal `ssh server` route. The server receives no GitHub token, checkout, or `node_modules`. Hidden activation fixes the target boundary, rejects unsafe ownership/symlinks, serializes mutation with a process-bound lock, and uses a private fsynced journal to restore prior links after interruption or failed backend/Caddy verification. The PC then independently verifies the production HTTPS JSON, MIME, links and SHA-256.
- Release versions are canonical SemVer-shaped UTC `YY.M.D` values with one immutable Release per UTC day. A second same-day product change stays in the single unmerged `ship-pending` PR. Previous immutable generations are retained, and `rollback <version>` is available only after an explicit user rollback request and exact target verification.
- Repository settings are read back with the local `gh` identity. Settings changes require a specific mutating request, repeat protected-head readback immediately before each write, never inspect secret values, and fail closed on partial AMO pairs or unexpected policy state.
- The operating agent is the qualitative review layer. After the final source push and finalized PR body/high-risk notes, it reviews the exact current head and records a COMMENT review identifying that SHA through `gh`; any later source push requires all checks and a new exact-head COMMENT. External Codex GitHub App review, comment-triggered review, bot approval and custom review workflows are not dependencies. The sole-owner branch keeps zero required approvals, native PR, the four GitHub-Actions-bound checks, administrator enforcement and conversation resolution. GitHub auto-merge and generic unattended merge remain disabled.
- `npm run verify` includes formatting, generated-runtime drift checks, manifest/project/semantic-workflow validation, lint, web-ext lint, unit/security behavior tests, shared-module and non-vacuous VM-bundle coverage thresholds, dependency audit, deterministic build, and package-content audit. Signed release allowlists also require `LICENSE` and `NOTICE`. CI separately runs the real Firefox playback/update E2E.

## Sensitive data rules

Do not commit, paste, transmit, or store:

- cookies or request/response headers;
- full CDN/HLS URLs with query strings or fragments;
- signed policy/signature values;
- account/session identifiers;
- key-like values, UUIDs, or connection identifiers.

When adding fixtures, use only redacted path shapes and synthetic domains where possible.

## Reporting issues

For personal/private use, export the local diagnostics JSON from the popup. If opening a GitHub issue manually, include:

- extension version;
- Firefox version;
- redacted diagnostics JSON;
- popup `lastDecision` reason;
- active tab redirect target state.

Do not include full signed URLs or account/session details.
